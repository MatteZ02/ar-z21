# Development guide

> This guide is being written phase by phase. Release builds and EAS will be
> added in Phase 6.

## Setup on Windows

1. Install **Node.js** (LTS) and run `npm ci` in the repository.
2. For Android builds, install **Android Studio**. It brings the Android SDK, an emulator and a
   suitable JDK. Then set these, for example in _System → Environment Variables_:
   - `ANDROID_HOME` = `%LOCALAPPDATA%\Android\Sdk`
   - add `%ANDROID_HOME%\platform-tools` to `PATH` (for `adb`)
   - `JAVA_HOME` = the JDK bundled with Android Studio: the `jbr` folder inside the Android Studio
     install folder (by default `C:\Program Files\Android\Android Studio\jbr`)

   A separately installed JDK (e.g. Java 23) may not work with the Android Gradle plugin.
   Use the bundled one.

3. **Long paths.** The native C++ build creates paths over 260 characters, and fails with
   `ninja: error: Stat(…): Filename longer than 260 characters`. Fix it once per machine:
   1. Enable Windows long paths (PowerShell as administrator), then reboot:

      ```powershell
      Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' LongPathsEnabled 1
      ```

   2. The `ninja.exe` bundled with the SDK's CMake 3.22.1 (ninja 1.10) ignores that setting.
      Download `ninja-win.zip` from the
      [ninja 1.12.1 release](https://github.com/ninja-build/ninja/releases/tag/v1.12.1), and replace
      `%ANDROID_HOME%\cmake\3.22.1\bin\ninja.exe` with the `ninja.exe` from the zip. Keep the old
      file as a backup.
   3. Delete `android\app\.cxx` and `android\app\build` before building again.

   Mapping the project to a short drive letter with `subst` does not help: the paths are still too
   long, and Expo autolinking cannot find `package.json` at the root of a drive.

4. Check the setup with `npx expo-doctor`.

## Running a development build

The app needs a native UDP module (`modules/z21-udp`), so **Expo Go cannot be used**. Build a
development client once, and again whenever native code or native dependencies change:

```sh
npx expo run:android          # builds, installs and starts on the emulator or a USB device
```

The first build takes around 10 minutes. To build only for the emulator's CPU type, which is
faster, add `-PreactNativeArchitectures=x86_64` when running Gradle directly
(`cd android; .\gradlew.bat app:assembleDebug -PreactNativeArchitectures=x86_64`).

After that, day-to-day JS changes only need the dev server:

```sh
npx expo start --dev-client
```

The `android/` and `ios/` folders are generated by `expo prebuild` and gitignored. Do not edit
them by hand.

iOS builds need a Mac or EAS Build (cloud); see Phase 6.

## Tests and checks

```sh
npm test            # Jest: protocol and connection logic, no device needed
npm run lint
npm run typecheck
```

`src/connection/__tests__/udpIntegration.test.ts` runs the connection manager over real UDP
sockets against a tiny fake Z21 on `127.0.0.1`. If Windows Firewall asks about Node.js during
tests, it only needs local access.

## Testing against the dummy Z21 server

In Phase 1 the app opens a developer **Connection test** screen. It has:

- connect and disconnect;
- track power on/off and STOP;
- driving one loco and switching F0;
- a hex **protocol log**, also printed to the Metro console in dev builds.

### Android emulator

The emulator reaches the host PC at **`10.0.2.2`**. Run the dummy server on the PC, enter
`10.0.2.2` and port `21105` in the app, and connect.

### Physical phone on the same Wi-Fi

1. Find the PC's LAN address, e.g. with `ipconfig` (IPv4 Address, such as `192.168.0.20`).
2. Allow inbound UDP on port 21105 in Windows Firewall (PowerShell as administrator):

   ```powershell
   New-NetFirewallRule -DisplayName "Z21 dummy server (UDP 21105)" -Direction Inbound -Protocol UDP -LocalPort 21105 -Action Allow -Profile Private
   ```

   The Wi-Fi network must be set to _Private_ in Windows. Otherwise use `-Profile Any`.

3. Enter the PC's address in the app and connect.

### What to look for in the log

- `>>` is sent, `<<` is received, `--` is an info line.
- On connect, the first datagram is `08 00 50 00 01 00 00 00 07 00 40 00 21 24 05`: broadcast
  flags (basic only) plus a status request, combined in one datagram.
- The app counts as **connected only after the first reply**. A server that never answers
  `LAN_X_GET_STATUS` will never get past _connecting_.
- When idle, a keepalive (`07 00 40 00 21 24 05`) is sent about every 25 s.

## Changing colours

All colours are defined in [`src/theme/`](../src/theme/). Components never contain colour values;
they read semantic tokens from `useTheme()`. Linting fails if a colour such as `'#ff0000'` or
`'rgb(…)'` is written anywhere outside `src/theme/`.

The theme has two layers:

| File                   | What it contains                                                                                                 | When to edit it                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `src/theme/palette.ts` | The raw colour values (`red700: '#C62828'`, …)                                                                   | To change a shade everywhere it is used |
| `src/theme/colors.ts`  | Semantic tokens (`stopButton`, `statusShortCircuit`, …) for light **and** dark mode, pointing at palette entries | To change what a part of the app uses   |

Spacing, corner radii, font sizes and the minimum touch-target size are in `src/theme/tokens.ts`.

### Example: make the STOP button darker red

Option 1: change the shade itself. Every token using `red700` changes too:

```ts
// src/theme/palette.ts
red700: '#A31515',
```

Option 2: change only the STOP button by pointing its token at a different palette entry, in
both light and dark mode:

```ts
// src/theme/colors.ts
export const lightColors: ColorTokens = {
  // …
  stopButton: palette.red800,
};

export const darkColors: ColorTokens = {
  // …
  stopButton: palette.red800,
};
```

To use a completely new colour, add it to `palette.ts` first, then reference it from
`colors.ts`.

### Using colours in a component

```tsx
import {useTheme} from '../theme';

const StopButton = () => {
  const {colors, minTouchTarget} = useTheme();
  return (
    <Pressable
      style={{backgroundColor: colors.stopButton, minHeight: minTouchTarget}}
    >
      <Text style={{color: colors.textOnStopButton}}>{strings.stop}</Text>
    </Pressable>
  );
};
```

### Rules for safety colours

- Text on a status or STOP colour uses its matching text token (`textOnStatus`,
  `textOnEmergencyStop`, `textOnStopButton`). Keep a contrast ratio of at least 4.5:1 for text
  and 3:1 for icons and indicators. Check new values with any WCAG contrast checker.
- Never rely on colour alone. Always show the status as text or an icon as well, because some
  members are colour-blind.
