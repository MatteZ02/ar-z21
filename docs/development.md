# Development guide

How to set up, run, test and release Throttle. Architecture and conventions are in
[CLAUDE.md](../CLAUDE.md).

## Setup on Windows

1. Install **Node.js** (LTS) and run `npm ci` in the repository.
2. For Android builds, install **Android Studio**. It brings the Android SDK, an emulator and a
   suitable JDK. Then set these, for example in _System → Environment Variables_:
   - `ANDROID_HOME` = `%LOCALAPPDATA%\Android\Sdk`
   - add `%ANDROID_HOME%\platform-tools` to `PATH` (for `adb`)
   - `JAVA_HOME` = the JDK bundled with Android Studio: the `jbr` folder inside the Android Studio
     install folder (by default `C:\Program Files\Android\Android Studio\jbr`)

   A separately installed JDK (e.g. Java 23) may not work with the Android Gradle plugin.
   Use the bundled one.

3. **Long paths.** The native C++ build creates paths over 260 characters, and fails with
   `ninja: error: Stat(…): Filename longer than 260 characters`. Fix it once per machine:
   1. Enable Windows long paths (PowerShell as administrator), then reboot:

      ```powershell
      Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' LongPathsEnabled 1
      ```

   2. The `ninja.exe` bundled with the SDK's CMake 3.22.1 (ninja 1.10) ignores that setting.
      Download `ninja-win.zip` from the
      [ninja 1.12.1 release](https://github.com/ninja-build/ninja/releases/tag/v1.12.1), and replace
      `%ANDROID_HOME%\cmake\3.22.1\bin\ninja.exe` with the `ninja.exe` from the zip. Keep the old
      file as a backup.
   3. Delete `android\app\.cxx` and `android\app\build` before building again.

   Mapping the project to a short drive letter with `subst` does not help: the paths are still too
   long, and Expo autolinking cannot find `package.json` at the root of a drive.

4. Check the setup with `npx expo-doctor`.

## Running a development build

The app needs a native UDP module (`modules/z21-udp`), so **Expo Go cannot be used**. Build a
development client once, and again whenever native code or native dependencies change:

```sh
npx expo run:android          # builds, installs and starts on the emulator or a USB device
```

The first build takes around 10 minutes. To build only for the emulator's CPU type, which is
faster, add `-PreactNativeArchitectures=x86_64` when running Gradle directly
(`cd android; .\gradlew.bat app:assembleDebug -PreactNativeArchitectures=x86_64`).

After that, day-to-day JS changes only need the dev server:

```sh
npx expo start --dev-client
```

The `android/` and `ios/` folders are generated by `expo prebuild` and gitignored. Do not edit
them by hand.

iOS builds use EAS Build in the cloud; see [iOS builds with EAS](#ios-builds-with-eas).

## Tests and checks

```sh
npm test            # Jest: protocol and connection logic, no device needed
npm run lint
npm run typecheck
```

`src/connection/__tests__/udpIntegration.test.ts` runs the connection manager over real UDP
sockets against a tiny fake Z21 on `127.0.0.1`. If Windows Firewall asks about Node.js during
tests, it only needs local access.

## Testing against the dummy Z21 server

The app connects at start-up to the address saved in **Settings** (default `192.168.0.111:21105`).
To change it, open Settings, enter the address and tap **Connect**. The address is remembered.

For protocol details, **Settings → For developers → Connection test and protocol log** shows a
hex **protocol log** of the app's connection (also printed to the Metro console in dev builds),
with buttons for track power, STOP and driving one loco.

### Android emulator

The emulator reaches the host PC at **`10.0.2.2`**. Run the dummy server on the PC, enter
`10.0.2.2` and port `21105` in Settings, and connect.

### Physical phone on the same Wi-Fi

1. Find the PC's LAN address, e.g. with `ipconfig` (IPv4 Address, such as `192.168.0.20`).
2. Allow inbound UDP on port 21105 in Windows Firewall (PowerShell as administrator):

   ```powershell
   New-NetFirewallRule -DisplayName "Z21 dummy server (UDP 21105)" -Direction Inbound -Protocol UDP -LocalPort 21105 -Action Allow -Profile Private
   ```

   The Wi-Fi network must be set to _Private_ in Windows. Otherwise use `-Profile Any`.

3. Enter the PC's address in the app and connect.

### A real Z21 connected to the PC

A Z21 central unit has the fixed address `192.168.0.111` from the factory. If the PC is on another
network (e.g. `192.168.68.x`), give its Ethernet adapter a second address in the Z21's network
(PowerShell as administrator):

```powershell
netsh interface ipv4 set interface interface="Ethernet" dhcpstaticipcoexistence=enabled
netsh interface ipv4 add address "Ethernet" 192.168.0.50 255.255.255.0
```

The emulator then reaches the Z21 at `192.168.0.111` through the PC. To undo it:

```powershell
netsh interface ipv4 delete address "Ethernet" 192.168.0.50
netsh interface ipv4 set interface interface="Ethernet" dhcpstaticipcoexistence=disabled
```

Note: through the emulator, the Z21 is not on the phone's _local_ network, so Android 17's local
network permission is not exercised. Test that on a real phone on the layout's Wi-Fi.

### What to look for in the log

- `>>` is sent, `<<` is received, `--` is an info line.
- On connect, the first datagram is `08 00 50 00 01 00 00 00 07 00 40 00 21 24 05`: broadcast
  flags (basic only) plus a status request, combined in one datagram.
- The app counts as **connected only after the first reply**. A server that never answers
  `LAN_X_GET_STATUS` will never get past _connecting_.
- When idle, a keepalive (`07 00 40 00 21 24 05`) is sent about every 25 s.

## Building a release APK

Members install Android releases as an APK from GitHub Releases. Every release must be signed
with **the same key**: Android only installs an update over the existing app if the signature
matches. A lost key means every member has to uninstall the app (losing their vehicle library)
and install it again.

### 1. Create the signing key (once)

In PowerShell, using the Java that comes with Android Studio:

```powershell
& 'D:\Program Files\Android\Android Studio\jbr\bin\keytool.exe' -genkeypair -v `
  -storetype PKCS12 -keystore "$env:USERPROFILE\keys\throttle-release.jks" `
  -alias throttle -keyalg RSA -keysize 4096 -validity 10000
```

(Create the `keys` folder first. Use your Android Studio folder if it is not on `D:`.)
keytool asks for a password and a name. The name is stored in the certificate and appears in
every APK for as long as this key is used, so enter only what may be public: your own name, or
a neutral one such as "Throttle". Do not enter an organisation's name unless it has agreed to
publish the app. The other questions (organisation, city, …) can be left empty. Use the same
password for the key when asked.

**Back it up now**, before the first release, in at least two places that are not this PC, for
example a password manager (as an attachment) and an encrypted USB stick. Store the password
with it. Never commit the key: `*.jks` is gitignored, and the key lives outside the repository.

### 2. Tell Gradle where the key is (once per PC)

Create or edit `%USERPROFILE%\.gradle\gradle.properties` (outside the repository) and add:

```properties
THROTTLE_KEYSTORE_FILE=C:/Users/<you>/keys/throttle-release.jks
THROTTLE_KEYSTORE_PASSWORD=<password>
THROTTLE_KEY_ALIAS=throttle
THROTTLE_KEY_PASSWORD=<password>
```

Use forward slashes in the path. The config plugin `plugins/withReleaseSigning.js` reads these
properties. Without them a release build stops with a message pointing here; debug builds do not
need them.

### 3. Set the version

In `app.json`, for every release:

- `version`: the version members see, e.g. `0.2.0` (0.x while in development);
- `android.versionCode`: **one higher than the previous release** (1, 2, 3, …). Android refuses
  to install an update with the same or a lower number.

### 4. Build

```powershell
npx expo prebuild --platform android --clean
cd android
.\gradlew.bat app:assembleRelease -PreactNativeArchitectures=arm64-v8a,armeabi-v7a
```

`--clean` regenerates `android/` from `app.json`, so version and icon changes are picked up. The
architecture list covers real phones and keeps the APK small (emulators need `x86_64`). The APK is
`android\app\build\outputs\apk\release\app-release.apk`.

Check the signature (it must show your certificate, not "Android Debug"):

```powershell
& "$env:ANDROID_HOME\build-tools\<version>\apksigner.bat" verify --print-certs app\build\outputs\apk\release\app-release.apk
```

### 5. Test, then publish

1. Install the APK on a phone over the previous release (`adb install -r …` or by opening the
   file) and check that the library is still there.
2. Rename it to `throttle-<version>.apk` and create a GitHub release with tag `v<version>`,
   marked as a pre-release while in 0.x. Attach the APK and describe what changed.
3. Commit the version change and push the tag.

## iOS builds with EAS

iOS apps are built in Expo's cloud (EAS Build), so **no Mac is needed**. Two accounts are needed:

- an **Expo account** (free; an Expo organisation such as `alppirautatiet` lets several people
  share the project);
- an **Apple Developer Program** membership (99 USD a year). It is needed for _any_ install on a
  real iPhone through EAS, including your own test device; TestFlight and the App Store need it
  too. EAS creates and stores the certificates and profiles.

First time:

```powershell
npx eas-cli login
npx eas-cli init          # links the project; adds the EAS project id (and owner) to app.json
```

**Test on your own iPhone** (internal distribution):

```powershell
npx eas-cli device:create                 # register the iPhone (opens a link on the phone)
npx eas-cli build -p ios --profile preview
```

When the build is done, open its link on the iPhone to install. On first start, iOS asks
whether Throttle may find devices on the local network: this must be allowed, or the app cannot
reach the central unit (iOS blocks the traffic without an error). Test this explicitly. Also
test the import from the Files app.

**TestFlight / App Store:**

```powershell
npx eas-cli build -p ios --profile production   # build number increases automatically
npx eas-cli submit -p ios                         # uploads to App Store Connect
```

The iOS build number is kept by EAS (`appVersionSource: remote` in `eas.json`), not in
`app.json`, so a build never leaves an uncommitted change. The first build asks to initialise it;
answer with 1. `version` in `app.json` is still the version members see. (Android release builds
are made by hand and still use `android.versionCode` from `app.json`.)

The app must first be created in App Store Connect with the bundle ID
`fi.alppirautatiet.throttle`. TestFlight testers are invited from App Store Connect. Unlisted App
Store distribution is requested from Apple after the first version is approved. Store texts,
privacy answers and the review notes are drafted in [app-store.md](app-store.md).

The Swift UDP code (`modules/z21-udp/ios`) has not been compiled yet; the first EAS build is its
first test.

## Changing colours

All colours are defined in [`src/theme/`](../src/theme/). Components never contain colour values;
they read semantic tokens from `useTheme()`. Linting fails if a colour such as `'#ff0000'` or
`'rgb(…)'` is written anywhere outside `src/theme/`.

The theme has two layers:

| File                   | What it contains                                                                                                 | When to edit it                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `src/theme/palette.ts` | The raw colour values (`red700: '#C62828'`, …)                                                                   | To change a shade everywhere it is used |
| `src/theme/colors.ts`  | Semantic tokens (`stopButton`, `statusShortCircuit`, …) for light **and** dark mode, pointing at palette entries | To change what a part of the app uses   |

Spacing, corner radii, font sizes and the minimum touch-target size are in `src/theme/tokens.ts`.

### Example: make the STOP button darker red

Option 1: change the shade itself. Every token using `red700` changes too:

```ts
// src/theme/palette.ts
red700: '#A31515',
```

Option 2: change only the STOP button by pointing its token at a different palette entry, in
both light and dark mode:

```ts
// src/theme/colors.ts
export const lightColors: ColorTokens = {
  // …
  stopButton: palette.red800,
};

export const darkColors: ColorTokens = {
  // …
  stopButton: palette.red800,
};
```

To use a completely new colour, add it to `palette.ts` first, then reference it from
`colors.ts`.

### Using colours in a component

```tsx
import {useTheme} from '../theme';

const StopButton = () => {
  const {colors, minTouchTarget} = useTheme();
  return (
    <Pressable
      style={{backgroundColor: colors.stopButton, minHeight: minTouchTarget}}
    >
      <Text style={{color: colors.textOnStopButton}}>{strings.stop}</Text>
    </Pressable>
  );
};
```

### Rules for safety colours

- Text on a status or STOP colour uses its matching text token (`textOnStatus`,
  `textOnEmergencyStop`, `textOnStopButton`). Keep a contrast ratio of at least 4.5:1 for text
  and 3:1 for icons and indicators. Check new values with any WCAG contrast checker.
- Never rely on colour alone. Always show the status as text or an icon as well, because some
  members are colour-blind.
